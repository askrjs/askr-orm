# 0.5.0 ORM hardening evidence

Status: the API/runtime candidate and real PostgreSQL tooling fix are qualified
locally. PostgreSQL 16–18 hosted and installed workflow checks must pass before
#55 closes. The package is **not release-ready**: #53 and #54 still require the
complete coordinated candidate/website qualification and maintainer review.

## Assertion review and real adapters

Existing tests were read before adding probes. They already assert placeholder
ordering/inert quoted text, the PostgreSQL bind ceiling with real 70-column
batches, constraint normalization, caller-owned rollback, four nested SQLite
savepoints, same-file queues, concurrent PostgreSQL migration applicants, cursor
cancellation, and failed non-transactional migration resolution. Those scenarios
remain; the new work targets cleanup recovery and complete migration scripts.

Local qualification uses Node 24.21.0, Node's real SQLite adapter, and an isolated
PostgreSQL 18.6 cluster with its own target/shadow databases. It does not use or
reset a user's database. Hosted integration retains PostgreSQL 16/17/18 and adds
normal package gates on Linux, macOS and Windows.

## Confirmed runtime regressions

The 33 focused cases were run with adapter/migration source restored from base
commit `4cb035c32240bd54464e25fb947b01b5e2279595`, then restored to the candidate.
The original source fails 14 cases and passes 19 characterizations. Those
failures exercise several defects, not ten independent bug claims:

| Boundary                                      | Original behavior                                                                      | Candidate and asserted recovery                                                                                                                                                                                                              |
| --------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQLite script with a failing middle statement | Prepares only the first statement, reports success and writes an applied ledger entry. | Executes the complete driver-owned script; earlier table/data and the ledger row roll back; a corrected script applies afterward.                                                                                                            |
| SQLite successful script                      | Drops following statements, including text containing a quoted semicolon.              | Commits all statements and preserves `semi;colon` as a value.                                                                                                                                                                                |
| PostgreSQL successful script                  | Treats a multi-result array as one result and throws after successful execution.       | Executes a parameter-free script without interpreting result sets; both inserts and its ledger entry commit.                                                                                                                                 |
| PostgreSQL rollback/unlock failure            | Returns a connection with failed cleanup to the pool.                                  | Marks it poisoned and discards it, preserves the primary callback error, removes listeners, and obtains a fresh usable connection. Real connection termination also verifies no inserted row survives.                                       |
| PostgreSQL deallocation failure               | Skips client release when DEALLOCATE throws.                                           | Releases/discards once, removes the listener and permits a subsequent description.                                                                                                                                                           |
| SQLite root/nested rollback failure           | Leaves unrolled-back writes on a reusable connection, allowing later commit.           | Quarantines the adapter and closes its database; another adapter and a reopened file observe only committed recovery writes.                                                                                                                 |
| SQLite quarantine close failure               | The first attempted runtime fix skipped any later physical close after quarantine.     | Logical retirement and physical closure are separate; explicit close retries cleanup and releases queue ownership only after closure succeeds. Its additional RED case failed against the intermediate implementation before the refinement. |

No application SQL splitter was added. DatabaseAdapter.executeScript is optional;
the supported drivers own their script semantics, and custom drivers retain the
existing execute fallback. Non-transactional migrations keep their intentional
partial-state and explicit resolve policy.

## Transaction migration lifetime

Three real SQLite cases capture the transaction's migrations API, then invoke
plan, apply and resolve after the callback has ended. Original code bypasses the
client's lifetime guard: plan/apply succeed and resolve reaches migration logic.
The guarded API rejects every call before SQL and leaves root plan usable. The
installed package repeats all three retirement assertions. Calls started inside
a transaction still need to be awaited by the transaction callback.

## Hosted platform follow-up

The first new Windows package lane failed the existing generation/validation
case. Extending that case to a project directory containing spaces, # and %
reproduced a loader failure locally: a filesystem path was interpreted as URL
syntax and truncated before the project name. Converting the database entry to
a file URL fixes the local RED case and explicitly handles Windows drive paths.
The fixture now includes CLI error output in failed expectations. Of the 41
moved tooling function bodies, 40 remain token-identical; loadDatabases has this
single intentional boundary correction. This does not complete the distinct
PostgreSQL shadow workflow tracked below.

## PostgreSQL tooling qualification

The original real PostgreSQL probe found three stubs: reset always threw,
introspection returned database/schema identity rows, and description returned
no columns. The fake-driver unit fixture did not qualify these boundaries.
The real-adapter regressions and the normal installed workflow are documented in
[PostgreSQL tooling](postgres-tooling.md). They cover actual target aliases,
unreachable target, reset rollback, deterministic supported catalogs, protocol
metadata without executing queries, concurrent description, workflow lock
ownership, real generation/byte-validation/no-op, drift/stale-artifact failure
and replay recovery. Composite keys and quoted enum names receive native tests.

The final 18-case native tooling suite fails 17 cases against the previous merged
PostgreSQL/schema/private-tooling source at
`3f595754d7e2a3135cd0ed0f5ef67b05b306e82c`; unreachable-target refusal is one
passing characterization because the old reset stub refuses everything. These
are scenarios, not 17 independent bug claims. Additional refinement RED cases
caught quoted enum SQL, missing related-table creation order, generated constraint
name differences during explicit rename, four silently ignored physical schema
attributes, duplicate query output names, and repeated parameter declarations
rejected by TypeScript. The final candidate passes all 100 tests and the installed
TypeScript 6/7 workflow.
